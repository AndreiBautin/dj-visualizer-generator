# Demo data

## What "demo data" means for an app with no database

There is no database, no seed script and no user records to fabricate. What a visitor to this app
actually lacks is **an audio file and a piece of artwork** — and demanding a DJ mix before showing
anything is the difference between a portfolio piece someone tries and one they close.

So the fixture is a bundled sample mix and cover image, plus a `POST /jobs/sample` endpoint that
starts a real job from them. The reviewer clicks one button and watches the pipeline run.

## The dataset

| File | What it is | Size |
|---|---|---|
| `assets/demo/sample-mix.mp3` | 24 s, 44.1 kHz stereo, 192 kbps. A four-note pad chord (A2/E3/C♯4/A4) with a tremolo pulse and a 55 Hz four-on-the-floor thump, faded in and out. | ~564 KB |
| `assets/demo/sample-artwork.png` | 1000×1000 radial gradient captioned "SAMPLE / DEMO MIX / synthesized audio". | ~246 KB |

The artwork says what it is on its face. Nobody should have to wonder whether they are looking at
someone's real record sleeve.

Both are regenerated by [`scripts/generate-demo-assets.sh`](../scripts/generate-demo-assets.sh):

```bash
bash scripts/generate-demo-assets.sh
```

It needs only ffmpeg and the OFL-licensed fonts already in `assets/fonts/`.

## Why it exercises the app rather than just filling it

- **24 seconds** is long enough to cross the loop boundary. The renderer produces one rotation
  period and loops it, so a clip shorter than the rotation would never demonstrate the part most
  likely to be wrong.
- **A radial gradient with strong colour** makes the circular crop, the white border ring, the
  drop shadow and the blurred ambient background all visible at a glance. A flat-colour image
  would render "correctly" while showing nothing.
- **Square 1000×1000** is the shape real cover art is, so the crop path is the real one.
- **Audible content, not silence.** A silent demo video looks broken even when it is not.
- The endpoint accepts the render settings currently in the form, so preset, rotation speed and
  caption font are all exercisable from the demo path — every UI control does something without an
  upload.

## The barriers protecting personal data

The deployed app must never contain the operator's own mixes. That is guaranteed structurally, not
by care:

**1. Generated, never captured.** Every byte is synthesized by ffmpeg from `sine` sources and a
drawn gradient. There is no export, copy or capture step from any real device anywhere in the
pipeline. The generator script is committed, so the provenance is auditable rather than asserted.

**2. Nothing personal can arrive by accident.** The deployed instance starts with an empty
ephemeral disk and has no import path — no admin upload, no restore, no volume mount from a
developer machine. The only files it ships with are the two above.

**3. The fixture is tested, not trusted.**
[`DemoAssetSafetyTests`](../backend/tests/Api.IntegrationTests/DemoAssetSafetyTests.cs) scans both
files byte-for-byte on every CI run for email addresses, URLs, phone numbers, credential-shaped
tokens, private-key blocks, and Windows or Unix home-directory paths. It decodes as Latin-1 rather
than UTF-8 so no byte run can be dropped as invalid and thereby hide a match.

It also checks container metadata *structurally*, because that is where an exported file gives
away the person: the PNG must carry no `tEXt`/`iTXt`/`zTXt` chunks, and the MP3's ID3v2 tag must
contain **only** ffmpeg's own `TSSE` encoder frame — no `TIT2` title, `TPE1` artist, `COMM` comment
or `APIC` embedded art — with no ID3v1 tag at the end either. If someone quietly swaps in a real
track, that test fails.

**4. `jobs-data/` is gitignored wherever it appears.** The ignore rule is unanchored, because the
Api and Worker each fall back to a `jobs-data` directory beside their own content root when
`Jobs__RootPath` is unset. See [SECURITY.md](SECURITY.md) F-4 — this was a real hole, found and
closed during this work.

## How the sample endpoint works

`POST /jobs/sample` with an optional JSON body:

```json
{ "title": "Sample Demo Mix", "preset": "720p", "rotationSpeedSeconds": 3, "captionFont": "sans-bold" }
```

Every field is optional. It opens the two bundled files as streams and calls **the same
`CreateJobUseCase`** an upload goes through — same validation, same signature checks, same size
limits, same queue. Only the source of the two streams differs. That is deliberate: a demo path
that bypassed the real pipeline would demonstrate the wrong thing.

Behaviour worth knowing:

- **Off by default.** `Demo:Enabled` is false unless a deployment sets it, so a private or
  self-hosted instance does not silently grow a public endpoint it never asked for.
- **404 when disabled**, so a disabled instance is indistinguishable from one that never had it.
- **503, not 404, when the assets are missing** — that is a deployment fault, not a caller error —
  and the response body never names the paths that were probed.
- **Rate-limited** by the same `job-creation` policy as uploads.

The frontend shows the button when built with `VITE_SAMPLE_ENABLED=true`, which the
single-container Dockerfile sets alongside `Demo__Enabled=true`.

## Resetting

There is no seed step and therefore no reset step. Jobs are created by visitors and deleted by
`CleanupService` once they pass `Worker__RetentionMinutes` (30 minutes on the demo, 60 by default).
On the free tier the disk is ephemeral as well, so a restart clears everything.

If you need to wipe a self-hosted instance immediately, delete the jobs root:

```bash
docker compose down -v
```

The bundled assets live in the image, not the volume, so they survive that and require no
re-seeding.

## Demo credentials

**There are none, because the app has no login.** Anyone can open the live URL and use it
immediately. This is called out here and in the README so a reviewer does not go looking for a
sign-in that does not exist.
